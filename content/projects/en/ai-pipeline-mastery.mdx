## The shape of the course

Most introductions to deep learning start from theory and arrive at code. This one starts from a complete PyTorch training pipeline and works backwards into the theory of each link: **Dataset → DataLoader → Model → Training loop → Validation.**

The four parts are four questions:

1. **Data Pipeline** — how does data get from disk into the model?
2. **Model** — what is "learning" actually adjusting?
3. **Training Loop** — what do the four steps of one iteration do?
4. **Validation** — how do you know a model is genuinely good rather than memorising?

Every concept is taught on the same thread: the line of code, what it runs, the theory it rests on, and the failure you see when it is wrong. The last one matters most — a concept you have only seen working is a concept you cannot debug.

## The portal

Delivering a course is a systems problem, not a content problem, so the second repository is a real application: an admin publishes lessons and materials, a student signs in and downloads them.

The security rule runs through the whole design: **the browser never speaks to the data store.** The client uses authentication only to obtain an identity token; every read and write goes through a server that has verified the session cookie, file downloads are handed out as time-limited signed URLs, and the database rules deny everything by default.

That constraint is also what separates the portal from the course landing page — the landing page is a static export, the portal needs a server to verify sessions and sign URLs, so they are two apps deployed independently.

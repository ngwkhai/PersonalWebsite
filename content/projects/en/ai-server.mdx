## Why split it at all

The first version did everything on one machine, which is the natural thing to build and the wrong thing to run. A model is the expensive part, and it is the part that wants a GPU; a webcam, a dashboard and a small database want to be near the room they are watching.

So the system became two: a **client** that owns the camera and all state, and an **inference service** that owns the model. They meet at one endpoint — `POST /api/detect`, an image in, detections out.

## What the split buys

The client no longer needs a GPU at all, so it runs on whatever machine is already in the room. The model can move — a different GPU, a different host — without touching the client, because the contract between them is a JSON response, not a shared process.

The response is deliberately small: counts per class, a score, a classification and the boxes with confidences. Everything else — drawing the boxes, keeping history, deciding what counts as an alert — stays on the client, where the state already lives.

## Cost, and what it forced

Sending every frame over the network would make latency the bottleneck instead of the model. Two things fix most of it: **skip frames** — inference does not need every one — and **cap the frame width** before uploading, since the detector does not benefit from resolution the model immediately downsamples away.

On the model side, exporting to **ONNX at half precision** was the other half: the same weights, a runtime built for inference rather than training, and a smaller memory footprint per request.

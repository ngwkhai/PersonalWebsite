## The problem

The first version did everything in one process: it read the camera, ran the model, served a dashboard and wrote to a database. The model needed a GPU, while everything else needed to stay near the camera.

## Split along state

The client owns everything stateful: capture, the annotated stream, local storage and a status API. The inference service owns only the model and holds nothing between requests, so it can be moved, scaled or rebuilt without the client noticing. The video source is set by configuration and can be a local device or a network stream, with automatic reconnection.

## Engineering the link

Frames are downscaled to a fixed width before they are sent, and the detections are rescaled so the boxes line up on the full-resolution stream. Inference runs on sampled frames rather than every frame, so the video keeps its frame rate while the network and the GPU carry only a fraction of the load.

## Failing well

When the remote call fails, the client runs the model locally, so the system stays available even without the GPU. Every remote call is timed and reported along with the backend that served it. Alerts fire when the state changes, with a limit on how often they can repeat, and storage is written at fixed time intervals instead of on every frame.

## Cheaper to serve, anywhere

The model runs as half-precision ONNX, and the format (PyTorch, ONNX or TensorRT) is chosen when the model loads. Loading happens at startup, so no request pays the cold-start cost, and the health endpoint reports which model file is actually loaded. The same app runs on a notebook GPU behind a tunnel, as a Docker image, and as a serverless GPU function.

## A deterministic core

The rules package has no dependencies, no clock and no randomness. Because of that, the same code can run in the browser for instant feedback and on the server as the authority. Matches can be stored as move logs and replayed, and search algorithms can simulate moves against the real rules.

## One interface, any game

Rules plug in through a single typed interface: initialise a match, apply an action, list the legal moves, report the outcome, and project the state for rendering. The server never reads a match's fields directly, so adding a new game only takes a rules package and a render layer.

## The schema is the API and the test

Zod schemas validate every inbound message. The same schemas generate `/openapi.json` and a live spec of the fourteen WebSocket messages, which OpenAPI cannot describe on its own. On every release, a drift suite checks the design document against the spec that the deployed service actually serves.

## Realtime, defended

The server is the only authority on game state. Each connection has a token-bucket rate limit and a cap on frame size, can reconnect with an opaque token, and is recorded in an audit log. The Fischer clock is owned by the server and kept out of the game state.

## Tournaments and delivery

Bot tournaments run as a separate service on Postgres with hand-written SQL. API keys are stored as hashes and compared in constant time, standings come from a SQL view, and matches are stored as action logs that can be replayed. Two bots, one using minimax with alpha-beta pruning and one using MCTS, were built to load-test the service. Both services deploy to Cloud Run through GitHub Actions without stored credentials. Each release has to pass contract tests, Playwright tests and a WebSocket smoke test against the real deployment.
